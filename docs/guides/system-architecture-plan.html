filemem-bench · architecture plan · v0.1

Addressable memory, then bakeoff

Build a filesystem memory system where IDs/locations open universes, fetches are bookkeeper-first, each step gets a fresh context, then measure it against RAG and other arms on the same suites.

01 · Goal

What we are trying to prove

  • Not “ship LangChain.” Not “bench for its own sake.”
  • Question: is addressable filesystem memory better (or good enough) vs RAG / alternatives under local constraints?
  • Method: build our system → same tasks → scorecard + optional HITL writeups.
  • Hardware: consumer GPU (RTX 3070), Ollama, reproducible ledgers.

02 · Core idea

Sparks open universes

Vector DBs find neighbors. We remember addresses. A small cue resolves to an ID/path; that locus reveals a structured packet of memory.

cue / spark→ universe id / path→ fetch brief→ fresh answer step→ write artifact

Disk is long-term memory. Context windows are disposable scratchpads.

03 · Architecture

Roles in the system

Orchestrator
Maps goal → universe(s) → next step. Short memory: ids, not whole files.
Bookkeeper prefer
Deterministic fetch inside one universe root: list / read / grep / field get.
Runner if needed
Lesser (or same) model: compress / disambiguate only when deterministic miss.
Writer / answerer
Fresh-window agents: manage universes or answer from a brief + citations.

Hard rules

  • One universe per fetch
  • Known path ⇒ no LLM fetch
  • New session per step (clear KV)
  • All artifacts land in the run ledger
  • Paths relative + canonical (/)

04 · Runtime flow

One query, step by step

1. Orchestrator: resolve "Morgan drink?" → universe:morgan / people/morgan.md 2. Bookkeeper: read people/morgan.md (cap bytes) → brief.json + citations 3. If miss/ambiguous: Runner summarizes only that universe → brief 4. Answerer (fresh window): task + brief → answer + real paths 5. Ledger: trajectories/, briefs/, search_outputs/, scorecard

Manage path is parallel: writer mints/updates universe files; bookkeeper never invents paths.

05 · Context vs VRAM

Fresh windows on one GPU

What we reset each step

Chat/session + KV cache. Short prompts. Orchestrator does not accumulate the whole store.

What usually stays

Model weights in VRAM (~5GB for 7B Q4). Sequential calls, not two fat contexts at once.

Best fetch

Deterministic bookkeeper: zero model VRAM for that step.

Optional swap

Unload big ↔ small model only if needed; pay load time. Default: same instruct, new session.

06 · Framework choice

Homegrown graph, not LangGraph-core

NeedOur equivalentLangChain/Graph
Orchestration Thin step runner in amb Optional later, not source of truth
State Disk: universes, briefs, ledger In-graph state (easy to hide)
Tools memory_tool_v1 + bookkeeper ops Tool wrappers
Trace / repro Run folder artifacts LangSmith etc. — out of critical path

Bakeoff fairness demands we own every step. Frameworks are sugar, not the spine.

08 · Bakeoff arms

Same suite, competing systems

A · Ours

Addressable FS + bookkeeper + fresh windows (+ organized manage).

B · Verbatim FS

Chunk dump, little curation — organization ablation.

C · RAG

Embed same stream, top‑k retrieve, answer with citations to chunk ids.

  • Pinned: suite version, seeds, prompts/digests, embed model, top‑k, num_ctx
  • Report: pass rate and latency / tokens / #LLM calls / VRAM peak
  • Later arms optional: full-context, hosted memory — only if inputs matched

09 · Scoring lanes

Headline vs human depth

Lane 1 — Scorecard headline

  • Facts present / update precedence
  • Protected survives
  • Answer match + real citations
  • Abstain when unknown

Lane 2 — HITL writeups secondary

  • Rubric: structure, trust, usefulness
  • Blind arms when possible
  • Never overrides scorecard win/loss
  • Stored in ledger with the run

10 · Low-level contracts

Nitpicks we will enforce

Addresses & tools

  • Relative paths, / canon
  • Strict tool schema; reject unknowns
  • Citation must exist on disk
  • Alias → id index file

Fetch & sessions

  • Byte caps on reads
  • UTF-8 / \n even on Windows
  • Per-step token + ctx logging
  • Atomic writes + end manifest hash

12 · Success

What “done” means

  • Near: smoke live — non-empty organized store, real citations, stable re-run.
  • System: spark → universe → bookkeeper brief → fresh answer, mostly without LLM fetch.
  • Science: bakeoff table vs verbatim + RAG you can reproduce from the ledger.
  • Not success: mock-only wins, framework demos, HITL overriding a lost scorecard.
